## 第2页：项目背景与动机

**标题**
**为什么选择这个项目？**

**核心问题**
- 开源游戏引擎在 MMO 领域的应用探索较少
- 现有方案多为商业引擎（Unity、Unreal）或完全自研
- Godot 4.x 带来了强大的网络能力，但缺乏 MMO 级别的参考实现

**项目目标**
1. 验证 Godot 引擎在 MMO 场景下的可行性
2. 构建可复用的游戏框架，降低 MMO 开发门槛
3. 探索现代微服务架构在游戏后端的应用
4. 为开源社区提供高质量的参考实现

**演讲稿（约1分钟）**
选择这个项目的初衷，源于我对开源游戏引擎的浓厚兴趣。Godot 作为一款轻量级、开源的游戏引擎，在独立游戏领域广受欢迎，但在大型多人在线游戏领域却鲜有成功案例。我们希望通过这个项目，填补这一空白。

项目的主要目标有三个层面：技术层面，验证 Godot 4.x 新一代网络协议在 MMO 场景下的实际表现；工程层面，构建一套可复用、可扩展的游戏框架，让其他开发者能够在此基础上快速构建自己的 MMO 游戏；社区层面，为开源世界贡献一个高质量的参考实现，推动开源游戏引擎的发展。

## 第3页：整体架构概览

**标题**
**混合架构设计**

**架构图**
```
                    ┌─────────────────┐
                    │  Godot 客户端   │
                    └────────┬────────┘
                             │
              ┌──────────────┴──────────────┐
              ▼                             ▼
     ┌─────────────────┐          ┌─────────────────┐
     │  Gateway 服务器 │          │  API 网关       │
     │   (GDScript)    │          │  (Ocelot/5000)  │
     └────────┬────────┘          └────────┬────────┘
              │                             │
              ▼                             ▼
     ┌─────────────────┐          ┌─────────────────┐
     │  Master 服务器  │◄────────►│   微服务集群    │
     │   (GDScript)    │          │  (.NET/Consul)  │
     └────────┬────────┘          └─────────────────┘
              │
              ▼
     ┌─────────────────┐
     │  World 服务器   │
     │  (游戏逻辑)     │
     └─────────────────┘
```

**设计理念**
- **关注点分离**：通用业务 vs 游戏逻辑
- **技术选型最优**：微服务处理数据，Godot 处理游戏
- **渐进式迁移**：保持 GDScript 服务器，逐步迁移到 .NET

**演讲稿（约1分30秒）**
现在让我介绍项目的核心架构设计。我们采用了创新的混合架构，将整个系统分为两层。

第一层是 Docker 容器化的微服务后端，负责通用业务逻辑，包括用户认证、数据持久化、服务发现等。这一层使用 .NET 10.0 和 ASP.NET Core 构建，采用现代云原生设计模式，具有高可扩展性和高可用性。

第二层是 Godot Headless 服务器，负责实时游戏逻辑、物理模拟和场景同步。这一层保留使用 GDScript 开发，因为 Godot 引擎在游戏逻辑处理方面具有天然优势。

两层之间通过 HTTP 和 WebSocket 进行通信，实现了技术栈的有机结合。这种设计让我们能够发挥每个技术栈的优势，同时在架构重构过程中保持系统的稳定运行。

## 第4页：微服务架构详解

**标题**
**基础设施层 - .NET 微服务集群**

**服务矩阵**

| 服务 | 端口 | 职责 | 技术栈 |
|------|------|------|--------|
| **API Gateway** | 5000 | 统一入口、路由转发、JWT认证 | Ocelot |
| **Auth Service** | 5001 | 用户注册、登录、令牌管理 | JWT + PostgreSQL |
| **Game Service** | 5002 | 角色数据、游戏规则、持久化 | EF Core |
| **Room Service** | 5003 | 房间管理、匹配逻辑 | 内存缓存 |
| **Chat Service** | 5004 | 实时聊天、消息推送 | SignalR |

**支撑设施**
- **Consul** (8500): 服务注册与发现
- **PostgreSQL** (5432): 核心数据库
- **Redis** (6379): 高速缓存
- **Jaeger** (16686): 分布式追踪

**演讲稿（约1分30秒）**
微服务层是整个系统的数据基础，包含五个核心服务。

API Gateway 作为统一入口，使用 Ocelot 实现路由转发和负载均衡，同时集中处理 JWT 认证，简化了下游服务的开发。

Auth Service 负责用户认证，支持邮箱登录和游客模式，使用 PostgreSQL 存储用户信息。

Game Service 是游戏逻辑的核心，处理角色创建、数据持久化等业务，通过 Entity Framework Core 与数据库交互。

Room Service 管理游戏房间的生命周期，包括创建、销毁、玩家匹配等功能。

Chat Service 基于 SignalR 实现实时双向通信，支持世界频道、私聊、系统广播等多种聊天模式。

所有服务通过 Consul 进行服务注册和发现，实现了真正的分布式架构。

## 第5页：游戏服务器层

**标题**
**游戏服务器层 - Godot Headless**

**三服务器模型**

**1. Gateway Server (:8088)**
- 职责：客户端连接入口、负载均衡
- 处理：Token 验证、连接转发
- 特性：支持大量并发连接

**2. Master Server (:8064/:8062)**
- 职责：中央协调器、节点管理
- 功能：
  - 管理 Gateway 和 World 节点注册
  - 维护服务器状态
  - 连接微服务后端

**3. World Server (:8087)**
- 职责：游戏逻辑执行、物理模拟
- 特性：
  - 10 物理 tick/秒
  - 每实例最多 200 玩家
  - 支持多地图实例

**演讲稿（约1分30秒）**
游戏服务器层采用经典的三服务器模型，这是 MMO 架构的最佳实践。

Gateway Server 是玩家连接的第一站，负责验证 Token 并将玩家分配到合适的 World Server。它就像一个智能负载均衡器，确保各 World Server 的负载均匀。

Master Server 是整个系统的协调中心，管理所有 Gateway 和 World 节点的注册与状态。它还负责与微服务后端通信，获取玩家数据、同步游戏状态。

World Server 是实际的游戏逻辑执行者，每个 World Server 可以运行多个地图实例。我们使用自定义的字节打包网络协议，通过 StateSynchronizer 实现高效的状态同步，关键路径包括位置、朝向、动画、皮肤等。

这种分层设计使得系统可以轻松扩展——当玩家数量增长时，只需增加更多的 World Server 实例即可。

## 第6页：核心技术亮点

**标题**
**核心技术实现**

**1. 自定义网络协议**
```
PackedByteArray 字节打包
├── StateSynchronizer: 基线 + 增量同步
├── PathRegistry: 路径到字段ID映射
└── 区域优化: 仅同步可见区域
```

**2. 数据请求模式**
```gdscript
InstanceClient.request_data("inventory.get", callback)
InstanceClient.subscribe("chat.message.send", handler)
```
- 15+ 数据处理器（战斗、属性、聊天、公会等）
- RPC 异步调用模式
- 统一的错误处理

**3. 状态同步优化**
- 关键路径: `:position`, `:anim`, `:skin_id`
- 带宽节省: 整数字段ID代替完整路径
- 基线压缩: 仅发送变化部分

**演讲稿（约1分30秒）**
在技术实现上，我们有几个核心亮点。

首先是自定义网络协议。我们没有使用 Godot 内置的 MultiplayerSynchronizer，而是实现了自己的字节打包协议。这让我们获得了更精细的控制，可以实现更高效的带宽利用。PathRegistry 将属性路径映射为整数字段 ID，大大减少了网络传输的数据量。StateSynchronizer 使用基线和增量同步，只发送变化的部分，进一步优化了网络性能。

其次是数据请求模式。我们定义了一套统一的 RPC 接口，客户端可以通过 request_data 或 subscribe 方法与服务器交互。目前实现了 15 个数据处理器，覆盖了战斗、属性、聊天、公会等核心功能。

第三个亮点是状态同步优化。我们识别了游戏中的关键同步路径，包括位置、动画、皮肤等，针对这些路径进行了特别优化。通过整数字段 ID 代替完整路径、基线压缩、区域可见性裁剪等技术，实现了在有限带宽下支持大量玩家同时在线。

## 第8页：技术栈总结

**标题**
**技术栈全景图**

**Godot 原生部分**

| 组件 | 技术选型 |
|------|----------|
| 引擎 | Godot 4.5 (GL 兼容模式) |
| 语言 | GDScript |
| 网络 | WebSocketMultiplayerPeer |
| 序列化 | 自定义 PackedByteArray |
| 数据存储 | QAD 格式 (.tres 资源) |

**微服务部分**

| 类别 | 技术选型 |
|------|----------|
| 框架 | .NET 10.0, ASP.NET Core 10.0 |
| API 网关 | Ocelot 23.4.2 |
| 服务发现 | Consul 1.15 |
| 实时通信 | SignalR |
| 数据库 | PostgreSQL 15 + EF Core 10.0 |
| 缓存 | Redis 7 (StackExchange.Redis) |
| 认证 | JWT Bearer |
| 追踪 | OpenTelemetry + Jaeger |
| 序列化 | MemoryPack 1.10.0 |
| 容器化 | Docker + docker-compose |

**演讲稿（约1分钟）**
项目的技术栈分为两大部分。

Godot 原生部分使用 GDScript 开发，利用 Godot 4.5 的新一代网络能力，实现了自定义的字节打包协议。数据存储使用 QAD 格式，这是一种基于 Godot 资源系统的轻量级数据库格式。

微服务部分完全采用 .NET 技术栈，使用最新的 .NET 10.0 和 ASP.NET Core 10.0。API 网关使用 Ocelot，服务发现使用 Consul，实时通信使用 SignalR。数据持久化使用 PostgreSQL 配合 Entity Framework Core，缓存使用 Redis。

整个系统通过 Docker Compose 进行容器编排，实现了"一键启动"的开发体验。我们还集成了 OpenTelemetry 和 Jaeger，实现了分布式追踪，方便问题定位和性能优化。

## 第9页：开发与部署

**标题**
**快速启动指南**

**开发环境启动**

**步骤1：启动后端基础设施**
```bash
cd GameBackend
docker-compose up -d
```
自动启动：Consul, PostgreSQL, Redis, API Gateway, 各微服务

**步骤2：启动 Godot 服务器**
```bash
# Master Server
godot --headless source/server/master/master_main.tscn

# Gateway Server
godot --headless source/server/gateway/gateway_main.tscn

# World Server
godot --headless source/server/world/world_main.tscn
```

**步骤3：启动客户端**
```bash
godot source/client/client_main.tscn
```

**服务访问地址**
- API Gateway: http://localhost:5000
- Consul UI: http://localhost:8500
- Jaeger UI: http://localhost:16686

**演讲稿（约45秒）**
项目的部署非常简单。后端基础设施通过 Docker Compose 一键启动，包括所有微服务和支撑设施。

Godot 服务器通过三个独立的 Headless 实例运行，可以在本地开发时快速启动和调试。

客户端则通过 Godot 编辑器或命令行启动，连接到本地或远程服务器。

整个启动流程经过精心设计，确保开发者能够在最短时间内搭建起完整的开发环境。

## 附录：答辩准备要点

**可能的问题及回答要点**

**Q1: 为什么选择混合架构而不是纯 .NET 或纯 Godot？**
A: 混合架构让我们能够发挥两个技术栈的优势。.NET 微服务擅长处理通用业务逻辑（认证、数据持久化、聊天），而 Godot 在游戏逻辑和物理模拟方面具有天然优势。这种设计既保证了系统的可扩展性，又保持了游戏逻辑的开发效率。

**Q2: 如何保证微服务和 Godot 服务器之间的数据一致性？**
A: 我们采用最终一致性模型。关键数据（如角色信息）由微服务持久化到数据库，Godot 服务器定期同步。对于实时数据，我们使用缓存和消息队列来保证一致性。分布式追踪系统帮助我们监控和调试数据流。

**Q3: 项目的主要挑战是什么？**
A: 最大的挑战是架构重构。我们正在从 GDScript 服务器迁移到 .NET 微服务，这需要在不影响现有功能的前提下进行。我们采用渐进式迁移策略，每个阶段都保持向后兼容，确保系统始终可用。

**Q4: 性能如何？能支持多少玩家？**
A: 目前每个 World Server 实例支持约 200 玩家。通过增加实例数量，理论上可以支持无限玩家。微服务层的性能测试显示，API 响应时间在 50ms 以内，ChatService 可以支持每秒 1000+ 消息。

**Q5: 下一步计划是什么？**
A: 短期计划是完成微服务迁移，优化网络同步。中期计划是进行大规模压力测试，优化性能。长期愿景是构建一个完全开源、社区驱动的 MMO 游戏引擎。
